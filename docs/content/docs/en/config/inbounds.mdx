An **inbound** is a listener that accepts client connections on a port using a
particular protocol and transport. Most of your day-to-day work is creating and
managing inbounds and the clients inside them.

## Create an inbound

<Steps>

<Step>
### Add an inbound

Open **Inbounds → Add**, give it a remark, pick a **protocol**, and choose a
**port** and listen address.
</Step>

<Step>
### Choose a transport and security

Pick the transport (TCP, WebSocket, gRPC, HTTPUpgrade, XHTTP, …) and the security
layer (none, TLS, or REALITY). See [Transports](/docs/config/transports) and
[REALITY](/docs/config/reality).
</Step>

<Step>
### Add clients

Add one or more clients, each with its own credential, limits, and share link.
See [Clients](/docs/config/clients).
</Step>

<Step>
### Set traffic limit, expiry, and reset

Optionally cap total traffic and set an expiry date for the inbound, and choose a
periodic **traffic reset** schedule: `never` (default), `hourly`, `daily`,
`weekly`, or `monthly`.

For `monthly` resets, select a day from 1 to 31. If the selected day does not
exist in a shorter month, the reset runs on that month's last day.
</Step>

</Steps>

## Supported protocols

The inbound editor accepts these protocols:

| Protocol               | Notes                                                                    |
| ---------------------- | ------------------------------------------------------------------------ |
| **VLESS**              | Lightweight; the basis for REALITY + XTLS-Vision. Recommended.           |
| **VMess**              | Older but very widely supported by clients.                              |
| **Trojan**             | TLS-based; supports XTLS and fallbacks.                                   |
| **Shadowsocks**        | Includes Shadowsocks-2022 (`2022-blake3-*`) ciphers.                      |
| **WireGuard**          | Modern tunnel.                                                           |
| **AmneziaWG**          | Obfuscated WireGuard fork, embedded in the panel process. See [AmneziaWG](/docs/config/amneziawg). |
| **Hysteria2**          | Selected as `hysteria`; the panel emits `hysteria2://` links.             |
| **HTTP**               | HTTP proxy.                                                             |
| **Mixed (SOCKS/HTTP)** | A combined SOCKS + HTTP listener.                                        |
| **Dokodemo-door / Tunnel** | Port forwarding / traffic redirect.                                 |
| **MTProto**            | Telegram MTProto proxy, served by a bundled `mtg` or `telemt` process (not Xray). |
| **TUIC**               | QUIC-based proxy protocol (v5), served by an in-process native Go server. See [TUIC](/docs/config/tuic). |
| **MASQUE**             | CONNECT-IP tunnel over HTTP/3 or HTTP/2, always behind TLS; delivered to clients through the JSON subscription. See [MASQUE](/docs/config/masque). |

<Callout type="info">
  Hysteria2 isn't a separate protocol internally — it's the `hysteria` protocol
  with the transport version set to 2, and the panel generates `hysteria2://`
  share links for it.
</Callout>

## Fallbacks — multiple protocols on one port

Fallbacks let a single TLS port (e.g. `443`) serve more than one protocol — for
example VLESS **and** Trojan — by routing unmatched handshakes to a child
inbound. In 3x-ui, fallbacks are managed in the panel (a master inbound's
**Fallbacks** list) rather than hand-written into JSON.

Fallbacks are available only when the master inbound is:

- **VLESS** or **Trojan**,
- on the raw **TCP** transport,
- with **TLS** or **REALITY** security.

Each fallback rule targets a child inbound and can match on `path`, `alpn`, and
`dest`. Client share links for a fallback child are automatically rewritten to
advertise the master's address, port, and TLS.

## MTProto relay

An MTProto inbound can run on a relay inside a censored network and send its
Telegram traffic on to a server outside it. Both parts are in the inbound form:

- **Relay → ServerHello MSS / Session MSS** (`network.clientMss`,
  `network.clientMssBulk`). Some DPI systems ban the proxy's IP and port when
  the FakeTLS ServerHello leaves in full-size TCP segments. With a ServerHello
  MSS set (for example `92`), mtg sends only the ServerHello in small segments
  and the rest of the session at the session MSS (`1400` by default). A session
  MSS of `0` keeps the whole session small. Linux only. Set them here or as
  `[network] client-mss` in the extra TOML, not both: a save with both is refused.
- **Route through Xray → Outbound.** The panel adds a loopback SOCKS inbound,
  tagged with the inbound's tag, to the Xray config, and points mtg's
  `[network] proxies` at it. With an outbound (or balancer) selected, it also
  adds a routing rule from that tag to it, so Telegram traffic leaves through
  the tunnel to the outside server. Without one, your routing rules decide.

<Callout type="warn">
  Xray's SOCKS inbound accepts a connection before it dials the target, so mtg
  cannot fall back from an unreachable IPv6 Telegram address. With **Route
  through Xray** on, an empty **IP preference** is saved as `prefer-ipv4`; if
  the selected outbound has no IPv6, `only-ipv4` fits too, and the form warns
  about `prefer-ipv6` and `only-ipv6`. Clients with an ad-tag do not work
  through the bridge, and the form warns about them too: the middle-proxy
  handshake is bound to mtg's own source address and port, which SOCKS hides.
</Callout>

The ServerHello settings need an mtg-multi build with `client-mss` support.
Older builds ignore them and start as before.

## MTProto backend: mtg-multi or telemt

**Backend** in the MTProto form picks the process that serves the inbound.
`mtg-multi` is the default, and inbounds saved before this option keep it.
[telemt](https://github.com/telemt/telemt) is a second backend. Client secrets
and share links are the same on both, so you can switch an inbound between them
and its existing links keep working.

telemt needs `bin/telemt-linux-<arch>` (release packages ship it for amd64 and
arm64) and version 3.5.17 or newer. For a node inbound, the binary must be on
that node. The node gets the setting through the usual sync. A save is refused
(HTTP 400) when the local binary is missing, when the inbound listens on a
hostname instead of an IP, or when Secured (`dd`) or WEB mode is on: telemt
serves plain FakeTLS (`ee`) clients only.

The panel owns every file telemt reads. They live in
`bin/mtproto/telemt-<inbound id>/`:

- `telemt.toml` holds the listener, the FakeTLS domains, the loopback API and
  metrics, and the Xray upstream. It ends with `include = "users.toml"`.
- `users.toml` holds only `[access.users]`, `[access.user_expirations]`,
  `[access.user_max_tcp_conns]` and `[access.user_ad_tags]`. It is built from
  the inbound's enabled clients that have traffic left.

telemt's API is read-only and bound to loopback. The panel never writes users
through it, so no second `[access.users]` table can end up in `telemt.toml`.

A client edit rewrites `users.toml` atomically, sends `SIGHUP`, then waits for
`GET /v1/config/state` to report the file published. telemt keeps running on
the old config when it rejects a reload. On a rejection the panel restores the
previous `users.toml`, logs telemt's reason, and does not retry until the client
set changes. Any other change restarts telemt. If telemt refuses to start with
the new config, the previous one is brought back.

Traffic quota and expiry stay with the panel. A depleted or expired client is
dropped from `users.toml` within one reconcile (10 s). The expiry is also passed
to telemt as `user_expirations`. Per-client traffic and online status come from
telemt's loopback Prometheus metrics.

Under **telemt settings** you can set a per-client TCP connection cap, plus extra
TOML merged under the generated `telemt.toml`, for example `client_mss` under
`[server]`. The keys the panel sets win. The extra TOML may not set any of these:

- `include`;
- `[access.users]` or other per-client `[access]` maps;
- `[server.api]`, the port, listeners or metrics;
- `tls_domain(s)`;
- `[[upstreams]]` while routing through Xray.

A `[[web.vhosts.profiles]]` entry must name a client of the inbound. A profile
whose client is disabled or depleted is left out of the generated config,
because telemt rejects a config whose profile names an unknown user.
